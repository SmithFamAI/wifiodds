# CLAUDE.md — conventions for wifiodds

Read this before touching anything. It encodes bugs that already cost real hours.

---

## ⚠️ FILE ACCESS: use Desktop Commander, not the built-in file tools

**On this machine, `~/Projects/wifiodds` is usually NOT connected to the Cowork session.** The
built-in `Read` / `Write` / `Edit` / `Bash` tools are scoped to the session's own outputs folder.
Point them at a path in this repo and they fail with:

    ...is outside this session's connected folders, so Write can't reach it.
    ...request it with the `request_cowork_directory` tool

which pops a folder-permission dialog at the user. In an interactive session that is an annoyance.
**In a scheduled task at 04:32 it is fatal.** The run stalls on a prompt nobody is awake to answer,
and the whole wave dies having done nothing.

So, for every file read, file write and shell command in this repo:

| Do | Do not |
|---|---|
| `mcp__Desktop_Commander__start_process` (host zsh) | the built-in `Bash` tool |
| `mcp__Desktop_Commander__read_file` | the built-in `Read` |
| `mcp__Desktop_Commander__write_file` / `edit_block` | the built-in `Write` / `Edit` |

Never call `request_cowork_directory` to work around it. If you think you need folder access,
something is wrong with your approach, so stop and say so.

**Passing work to a subagent?** Subagents do NOT inherit this. Put the rule in the prompt verbatim,
or the agent will hit the dialog and stall. This has already happened once.

Two more, both learned the hard way:

- **Run git through Desktop Commander, never workspace bash.** The workspace mount strands `.git`
  locks, and this repo is invisible to workspace bash entirely.
- **`~/websites` has the same property**, and it is where the strategy docs and mockups live.

## SHIPPING: `build/ship.sh`, and nothing else

    bash build/ship.sh "commit message"    # build, verify, stage, commit, push, ff main
    bash build/ship.sh --check-only        # build + verify, touch nothing

On 26 Jul 2026 the 04:32 refresh pushed a commit to `main` while `build/apitest.js` was failing six
checks. Production carried a red suite for 38 minutes and nothing said so. The gate was **not**
missing: the scheduled task's own prompt said "if it exits non-zero: do NOT commit, do NOT push".
It simply was not followed.

That is the third time this project lost to the same shape in two days. `.assetsignore` was believed
to keep files off the deploy and did nothing. A model doctrine was enforced in one shell script that
had been paused for eight days. And a verification rule sat in a prompt nobody executed.
**A rule that lives somewhere the runtime does not read is not a rule.**

`ship.sh` puts the gate in code, so any caller gets it whether or not they read this file. There is
also a pre-push hook for the case that actually bit us, a push that never went through `ship.sh`:

    sh build/install-ship-hook.sh     # once per clone; hooks are not versioned

On failure neither one aborts destructively. They push nothing and leave the tree exactly as the
build left it. That is deliberate: a process that takes the deploy down at 04:32 with nobody awake
is worse than the fault it guards against. Same doctrine as `reconcileUnited()` in
`build/prerender.js`, which heals and logs rather than exiting.

## VERIFY BY RESPONSE BODY, NEVER BY STATUS CODE

Three separate failures in this project returned HTTP 200. One served a zero-byte body that passed
every check for the life of the deployment. Always:

    curl -sS --compressed "https://wifiodds.com/?cb=$RANDOM" | grep -o '<title>[^<]*'

Always a fresh cache-buster. `web_fetch` caches silently; treat what it says as a hypothesis.

**`curl` cannot see a stale stylesheet, because it has no cache.** For anything visual, ask a
browser for a computed custom property. Twice, curl reported a deploy as perfect while the browser
rendered the old CSS.

**For anything about mobile layout, use a real mobile engine.** An iframe forced to 390px in desktop
Chrome is not a phone: same engine, same UA, same fonts. It reported "fits" three times while
Jeremy's phone showed the opposite. `~/websites/scripts/responsive/check.mjs` sweeps WebKit and
Chromium across 23 widths and checks two things: overflow, and whether landmark left edges agree.
The bug it was written for was the second kind, and no overflow test could ever have seen it.

## NEVER `git add .`

The tree holds other people's drafts and this rule has already caught a real staging mistake. Stage
by explicit path. `ship.sh` enforces it and refuses to guess about untracked files.

## The build owns the output

Every public page is generated by `build/lib/*` and written by `build/prerender.js`. **Never
hand-edit a file listed in `build/routes.js`.** A drift guard fails the build, and the next build
overwrites you anyway. Change the generator.

The deploy publishes the **repository root**, because the Cloudflare build output directory is
empty. That means every tracked file is a public URL: **29** internal files are served as of 26 Jul
2026, all of them already public on GitHub. `build/leak-canary.sh` reports what is exposed; it is
detect-only and must stay that way. See `~/websites/wifiodds-publication-audit.md`.

**Do not trust that number, and do not add a new one when it moves.** It has been written down as
26, 28, 21 and 29 in four places, and the count climbs every time anyone commits a build script,
because a new tracked file at the repo root is a new public URL. A count going from 28 to 29 is
indistinguishable from a leak. The fix is a committed manifest so a NEW NAME is the signal instead
of a bigger total; the design is in `~/websites/wifiodds-publication-default-deny-plan.md`.

**`leak-canary.sh` exits 1, not 0.** Two documents and one session said 0. All three had measured
it through a pipe, and `cmd | tail` reports `tail`'s status. Run it bare and read `$?`, or use
`${PIPESTATUS[0]}`. The script also prints a reassuring "Expected while the Pages build output
directory is empty" while returning non-zero, so its message and its exit code disagree. Believe
neither until you have run it bare.

## Prose is enforced

`build/slop-gate.js` runs at the end of every build and a pre-commit hook runs it on staged
`.md`/`.html`/`.txt`. Both are ratchets against each file's own recorded baseline, so you are never
blocked by prose you inherited, only by making a file worse than itself. Read
`~/websites/WRITING-STYLE.md` and load the `no-slop` skill before writing anything that ships.

Never set `SLOP_GATE=warn` in a scheduled task. Bless a baseline rarely, and say in the commit
message whether the linter or the file was at fault.

## Data rules that are not negotiable

- **Never invent a figure.** An agent once fabricated flight numbers, dates and routes for field
  reports. If there is no source, the answer is "no source found", written down.
- **Every figure carries a tier, a source and a date.** MEASURED / REPORTED / VENDOR CLAIM.
- **Publish the floor**, not the blend. Unresolved aircraft are excluded from the denominator and
  shown, never assumed into it.
- **The projected score has five fences** and `assertProjectedRender()` enforces them. It never
  sorts, never takes a band colour, always carries its horizon and confidence, and flips to SLIPPED
  keeping the date it missed. You may restyle the unit. You may not unfence it.
- **One aggregator poisoned two live numbers** on 26 Jul. A figure that appears in ten places can
  still have one source, and that source can contradict itself two scroll-lengths down. Trace to a
  publisher of record.
- **Unknown is not zero.** Setting a count to 0 to make an unsourced figure go away publishes a claim
  nothing supports, and it happened on 26 Jul. SAS's Starlink count went to `equipped: 0` against a
  fleet total left at 123, so the page read "0 of 123 (0%)" while its own note said Starlink launched
  24 Mar 2026. That is a false, sourced-looking zero on a fleet with some real coverage nobody has
  published a count for. The fix is `equippedPublished` / `nextGenPublished` (booleans) plus
  `pctEquipped()` returning `null`, never `0`, when the underlying count is unpublished. Every
  template has to read those flags before printing a number. A raw `equipped` field of 0 is ambiguous
  between "confirmed zero" and "unknown," and this codebase shipped exactly that bug once.

## `united/data.json`'s roster is Starlink-only

There is no system-by-segment crosstab in it. No Ka-band count, no ATG count, nothing broken out by
Viasat generation. It tracks one thing: which tails have Starlink, mainline vs regional. That means
the three-score model (`nextGenSplit` on all 18 airlines in `assets/airlines.js`, `nextGen.split` in
the API, `VALUE_SPLIT_ALLOWED = ['united']` as the apitest tripwire that fails if anyone estimates a
missing split for a non-United airline) produces three **NEXT-GEN ODDS**: the chance of drawing a
Starlink or Amazon Leo aircraft, split mainline and regional. It does not produce three ConnectScores.
ConnectScore still answers a different question, today's system quality, weighted and blended. Don't
conflate the two when writing about "three scores." It is one score plus a two-way split of the
next-gen number, not three independent scores of the same thing.

## The canonical-vs-device responsive checker trap

Two files both claim the job:

- `~/websites/scripts/responsive/check.mjs`, the canonical one, 4,768 bytes. Sweeps 23 widths in
  WebKit and Chromium and checks two failure classes: overflow, and whether landmark left edges agree.
  That second check catches the alignment bug an overflow test can never see. See `WIFIODDS-BOOT.md`'s
  "browser, not curl" section for the incident that wrote this.
- `~/.wo-respo/check.mjs`, a different and smaller script, 2,899 bytes. Imports only
  `webkit, chromium` (no `devices`), and does zero alignment checking. Confirmed by diff on 26 Jul.

`~/.wo-respo/` has a populated `node_modules/`. `~/websites/scripts/responsive/` does not, and ESM
resolution ignores `NODE_PATH`, so running the canonical script in place fails on missing `playwright`.
**Copy `~/websites/scripts/responsive/check.mjs` into `~/.wo-respo/` (next to its `node_modules`)
before running it.** Do not run whichever copy happens to be closer at hand. A session that
finds `~/.wo-respo/check.mjs` first will get a clean "no overflow" result that says nothing about
alignment, and will not know that's what happened.

## The prose ratchet: verified, not assumed

`build/slop-gate.js` does rewrite a page's baseline downward when the page's prose genuinely
improves. This was tested directly on 26 Jul instead of taking the code comment on faith: with
`index.html`'s recorded baseline temporarily edited to a higher `pivotUnits` (simulating a prior
state with more em dashes than today), `node build/slop-gate.js` printed `ratcheted DOWN index.html:
pivotPer1000 3.43 → 2.43` and rewrote the baseline file to match. The mechanism works. The edit was
reverted with `git checkout -- build/slop-baseline.json` right after. Nothing here changed a
committed number.

The nuance that made this look broken: **`pivotPer1000` only ratchets down when the underlying
`pivotUnits` count also fell**, not just the rate. That's deliberate. `build/slop-gate.js`'s own
comment explains that the roster growing every morning lowers the rate on its own (measured:
`/united/fleet/` fell from 1.71 to 1.37 on a simulated quarter of daily pulls with zero prose
changes). Ratcheting on rate alone would let the ceiling tighten itself unattended, and that is the
one way this gate could fail at 04:32. So a fix that doesn't reduce the actual dash count won't move
the baseline, even if the rate would look better on paper.

Separately, and worth checking before assuming a specific fix should have ratcheted anything: commit
`8c4edf3` removed the em dash from `fitBadge()`'s tooltip `title=""` attribute across several airline
rows, but `index.html`'s baseline sat at `pivotPer1000: 2.43` / `pivotUnits: 4.25` both before and
after a full rebuild. Whether `slop-check.js` reads text inside HTML attributes at all, as opposed to
only visible rendered text, was not confirmed in this pass. If it doesn't, that particular fix was
real (better markup, unrelated to the linter) but was never going to move the score. The 2.43 ceiling
would measure something else in that case, not unrepaid debt. Check `build/slop-check.js`'s HTML
extraction before concluding either way.
